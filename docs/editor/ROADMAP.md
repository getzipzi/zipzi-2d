# Kasane：Agent-first Live2D 编辑器产品路线图

更新：2026-09-19。

本路线图取代原 Stage 00–08 的线性验证计划。Stage 00–05 已证明内存数据、进程内脚本、可选 Action、变形求值和实时显示可以成立；这些成果成为产品基础，不再以新增演示场景作为主要进展指标。

本文描述目标产品、模块整合方式和交付顺序。下文架构与里程碑是待实施方向，不代表仓库已经具备相应能力。当前实现见 [架构说明](ARCHITECTURE.md)、[脚本接口](SCRIPTING.md) 和 [Stage 05 实现记录](stages/05-deformers.md)。

## 1. 产品目标

Kasane 要成为一个开放、可编程、由 Agent 主导创作的 Live2D 式 2D 角色编辑器，并让创作结果能够进入实际应用运行。

主要工作流程：

> 人提供素材、目标与约束 → Agent 组织模型、建立网格和绑定 → 制作参数驱动的形态 → 读取数据并观察画面 → 自行修正 → 人辅助检查 → 保存工程 → 在应用中驱动和播放。

Agent 是主要操作者和第一轮检查者。人负责表达意图、提供审美判断、指出问题以及必要的局部修正；人工逐次批准不构成建模流程的默认前置条件。

产品必须同时提供三个相互连接的部分：

| 部分 | 产品职责 |
|---|---|
| 创作数据与求值内核 | 表达素材、部件、网格、变形器、参数与关键形态，支持持续编辑并生成运行结果 |
| 编辑器应用 | 管理工程与会话，提供脚本执行、对象检查、画布、参数预览和可选编辑工具 |
| 运行时 | 在编辑器之外加载创作成果，以相同语义驱动、求值和渲染 |

“Live2D 式建模”“加载现有 Cubism 模型”“与 Cubism 工程及发布格式互通”是分别需要交付的能力。不能以其中一项代替另外两项，兼容范围见第 9 节。

## 2. 当前起点：已具备什么，缺少什么

### 可以继续使用的基础

- `kasane-core`：独立 C++ Document、稳定对象与顶点 ID、批量几何操作、Rotation 和受限 Warp 求值。
- `gd-kasane`：Godot 数据对象绑定、内存网格显示、预览更新、源数据快照和项目保存重开。
- 进程内 GDScript：直接操作当前模型，不经过逐操作 RPC，不强制事务；显式 Action 复用 Godot UndoRedo。
- `purism-core`：现有 MOC3 模型的兼容加载与求值实现，以及参数、插值、变形等算法资产。
- `gd-cubism`：现有模型接入与播放，以及已实现的绘制顺序、透明度、颜色、遮罩和批处理等渲染能力。
- 回归工具：核心测试、Godot 集成、真实 GPU 图像检查及 Cubism/Purism 对照基准。

### 尚未形成产品的部分

- 主要入口仍是固定样例；尚无完整工程工作台、真实素材管理和持续制作流程。
- 原生创作与 Cubism 播放各有一条显示路径，尚未共享渲染接口。
- `KasaneDocumentBridge` 同时承担源数据入口、资源、预览与文件操作；Session 边界尚未独立。
- 原生参数与 Keyform 尚未实现；Stage 05 的变形规则不能直接视为 Cubism 等价规则。
- Agent 具有基本脚本与观察能力，但仍缺少不依赖人工 Run/F5 的任务入口、完整执行反馈和多状态检查。
- 原生发布数据与独立应用加载契约尚未建立。

结论：停止重复证明基础可行性，开始把这些模块组织成同一个编辑器产品。已有样例保留为回归与教学材料，正式能力不应继续只存在于 `demos/`。

## 3. 模块整合与数据流

### 3.1 模块职责

| 模块或层 | 目标职责 | 整合方式 |
|---|---|---|
| `kasane-core` | 权威创作数据、数据操作、源数据到求值数据的转换 | 保留稳定身份与无 Godot 依赖；不承担界面、历史栈或脚本任务调度 |
| `purism-core` | Cubism 兼容后端、可复用的求值算法 | 保留原有 ABI 与回归；识别并提取不依赖 MOC3 布局的算法，不能直接把内部运行结构当成可编辑工程 |
| `gd-cubism` | 已有模型加载与播放适配 | 逐步将渲染器中的通用部分解耦；迁移期间维持现有路径可用 |
| `gd-kasane` | Godot 数据绑定与创作侧适配 | 暴露模型对象，连接 Session、求值和公共渲染层；拆分过大的 Bridge 职责 |
| 公共 Godot 渲染层 | 根据绘制数据显示模型 | 接收普通数据，不直接依赖 `CubismModel` 或编辑器 Document；具体目录在提取时确定 |
| Editor 应用 | 工程、Session、任务、检查界面与人机协作 | 建立独立应用入口；优先使用 Godot 已有设施 |
| `demos/`、`benchmarks/` | 回归、示例、性能与兼容对照 | 服务正式模块，不能代替产品入口或成为生产代码的依赖 |

模块是否合并目录服从代码职责，不以改名或搬文件作为整合完成的证据。保留来源与版权说明。

### 3.2 数据流

```text
Agent / 人工辅助界面
          │
          ▼
    Editor Session
          │ 直接数据访问 / 可选 Action
          ▼
    Authoring Document
          │ 内存转换与更新
          ▼
    原生求值状态 ─────────────────┐
                                 ▼
现有 moc3 → Purism 兼容求值 → 公共绘制数据 → 共享 Godot 渲染器
                                                   │
                                    编辑器画布 / 观察图 / 应用播放器
```

原生与兼容路径优先共享绘制契约。求值算法逐项整合，在语义一致和回归证据充分前允许保留两个后端；不靠强行套用相同结构来制造“已统一”。

### 3.3 三类数据的所有权

| 数据 | 所有者与用途 | 编辑规则 |
|---|---|---|
| 创作源数据 | Document：素材引用、几何、关系、绑定、关键形态 | 脚本可直接读写；保存工程时持久化 |
| 会话数据 | Session：当前工程、预览参数、历史、选择、脚本任务和观察结果 | 预览操作不写入基础形态或 Keyform |
| 派生数据 | 求值与渲染层：连续数组、依赖索引、求值位置、GPU 资源 | 可重建，不作为第二份可编辑源数据 |

结构修改可重建受影响的求值结构；数值修改更新相关数据与依赖。交互编辑不经过“导出文件 → 重新加载模型”。先采用明确、可检查的对象级更新，性能证据出现后再细化。

## 4. 两项优先整合工作

### 4.1 共享渲染契约

从 `gd-cubism` 的实际数据读取和绘制代码中提取边界，建立公共绘制数据：

- 稳定 Drawable 身份、顶点位置、UV、索引与纹理引用。
- 可见性、透明度、绘制顺序、颜色与所需混合模式。
- 遮罩关系，以及必要的变化标记和资源生命周期约定。
- 坐标方向、画布尺寸、缩放单位和纹理方向的明确转换规则。

原生求值和 Cubism 适配器分别提供这份数据；Godot 渲染层只消费它。优先接入真实制作所需的多图层与遮罩，再逐步迁移已有能力。

迁移要求：

1. 原有模型在迁移前后保留几何与实际画面对照。
2. 原生文档可使用同一渲染能力，不必构造 `CubismModel`。
3. 正常位置更新保留可复用的 GPU 资源。
4. 尚未迁移的特性明确保留原路径或报告不支持，不能默默降级画面。
5. 公共渲染层不因复用而要求原生模型加载 Cubism SDK 或 MOC3。

### 4.2 创作模型与求值后端

创作数据应方便新增、删除、重排和查询；运行数据应方便插值、变形和绘制。两者可以使用不同布局，但必须有明确的映射和失效规则。

参数与 Keyform 实施前，检查 Purism 的绑定、插值、变形和父子应用顺序：哪些是通用算法，哪些依赖文件布局或 Cubism 特定语义。为可提取部分建立普通数据输入和数值对照，再决定复用或替换原生实现。

Stage 05 的简单 Warp 作为已有原生语义保留记录。改变外推、局部坐标或嵌套规则时，必须考虑现有工程的版本与迁移，不能静默改变已保存模型的外观。

编辑器预览与原生发布播放器共享同一求值实现或经过一致性验证的同一计算契约；发布不能再实现一套近似算法。

## 5. Agent-first 编辑契约

### 5.1 数据访问是基础能力

- 通过 Godot 类型与属性绑定暴露创作对象，支持集合遍历、稳定 ID、关系查询、批量几何访问及所需的增删改。
- Agent 能发现可用类型、属性、读写能力和数据约束，不必只依靠硬编码示例或操作名称猜测接口。
- 脚本在应用进程内运行；高层建模配方与底层数据写入共用同一模型。
- 不要求所有修改成为 Command 或 Action，不自动为每次脚本执行创建事务。
- 明确数组复制、写回、对象生命周期、线程及无效数据规则。内存可编程不意味着默认开放任意裸指针。
- 对性能敏感的批量操作提供实际批量入口；不要以逐顶点远程调用模拟数据访问。

当前采用 GDScript。

### 5.2 Action、恢复与草稿按需使用

复用 Godot UndoRedo。Action 封装常用操作、记录恢复数据，并在需要时提供原子性；Godot UndoRedo 本身不保证任意操作失败后的自动回滚。

直接脚本发生错误时，已完成的数据修改可以保留，执行结果必须说明状态；显式 Action 仅在其承诺范围内恢复。现有整文档快照可继续支撑早期制作，随后根据实际内存和交互成本改进，不在数据层重新维护历史栈。

检查点、草稿和接受/拒绝流程是可选工具，Agent 也可自行使用。不得把所有建模工作改造成等待人工批准的提案队列。UI 和脚本不得维护两套编辑语义。

### 5.3 脚本执行与反馈

提供外部 Agent 可调用的应用任务入口，投递完整脚本并查询结果。投递机制在 Session 接入时选择；它只传递任务与观察请求，脚本的数据操作仍在应用内完成。

任务至少记录：执行 ID、目标会话、起止文档版本、状态、日志、结构化结果及观察产物。区分排队、运行、完成、失败；旧任务不得误写新打开的文档，失败不得伪装成“没有变化”。

首版可以串行执行可信的短脚本，不要求分布式调度。取消、超时和恢复能力必须与实际执行模型一致：同步阻塞的 GDScript 不能仅靠 UI 状态声称已经被安全终止。先提供可用的状态与恢复办法，再按需要扩展执行隔离。

### 5.4 观察是正式接口

Agent 需要同时获得数据与视觉证据：

- 对象摘要、依赖关系、基础形态、指定 Keyform 和当前求值结果。
- 全图、局部裁剪、对象定位或高亮，能够把画面问题对应到对象 ID。
- 明确参数状态下的截图、参数扫描接触表或连续帧。
- 实际所需的几何诊断，例如退化三角形、翻折或异常拉伸；诊断与最终视觉质量分开。

观察产物必须关联文档版本、预览参数和拍摄设置。求值或上传失败时不得把旧画面冒充当前结果。真实截图来自启用渲染的环境；headless 逻辑测试不能替代图像证据。

Agent 在同一工程中完成“检查 → 修正 → 再检查”。是否需要内置模型服务、聊天面板或 MCP，依据接入需求决定，不作为第一版能力证明。

## 6. 产品里程碑

使用 P1–P4 区别于历史 Stage 编号。每个里程碑交付一段可持续使用的产品工作流；下面的依赖表示交付依赖，不要求所有工作严格串行。

| 里程碑 | 实际能做什么 | 核心依赖 | 当前状态 |
|---|---|---|---|
| P1 创作工作台 | 在正式应用中打开工程、导入多图层素材、检查对象并运行脚本 | 现有源数据与脚本基础、公共渲染整合 | 待实施，下一交付目标 |
| P2 Agent 完成真实部件 | Agent 建立眼部网格、变形与睁闭眼参数，观察多个状态并自行修正 | P1、参数与 Keyform、任务与观察接口 | 待实施 |
| P3 持续角色制作 | 在同一角色工程中扩展多个部件，反复修正素材、绑定与形态 | P2 的真实使用反馈 | 待实施 |
| P4 应用交付 | 创作成果可发布并在独立应用中驱动，编辑与播放结果一致 | 原生求值契约及完整可用部件 | 待实施；早期即建立播放对照 |

### P1：从预览场景变成创作工作台

实施设计见 [P1 可交付实施文档](milestones/P1-implementation.md)，包含架构契约、P1.1–P1.4 分段、迁移步骤和验收矩阵；当前为设计状态。

**使用任务**：在正式 Editor 中建立或打开工程，导入一组眼部图层，保存其位置与组织关系；Agent 通过脚本调整对象，人可以定位和检查。

交付内容：

- 独立 Editor 应用入口，建立 Document / Session / Viewport 的职责边界。
- 工程新建、打开、保存，素材路径和缺失资源反馈；支持 PNG 图层、原画画布尺寸及图层位置。
- 多网格绘制顺序、透明度和所需遮罩，通过公共绘制接口复用现有渲染能力。
- 实用的画布缩放、平移、对象定位/高亮、对象与属性检查、脚本结果和错误反馈。
- 首版脚本投递与结果查询入口，能作用于当前 Session，不依赖人反复点击 Run。

完成标准：换一组符合输入约定的素材仍能完成同样工作，不修改 fixture 常量或演示程序源代码。工程关闭重开后可继续编辑；同一渲染层能够服务原生模型与已覆盖特性的现有模型。

此处需要真正可用的检查界面，不要求先实现完整人工网格工具或复杂停靠布局。

### P2：Agent 自主完成一个可驱动的真实部件

**使用任务**：Agent 根据分层素材和目标，在同一个工程里制作眼白、虹膜、眼皮，形成可驱动的睁闭眼变化，自行检查并至少进行一次有理由的修正。

交付内容：

- 参数范围、默认值、属性绑定、Keyform 的创作数据与脚本接口。
- 明确基础形态、指定关键值写入和会话预览参数的区别；不能隐式写到“当前附近的形态”。
- 先实现这个部件所需的插值和目标属性；先完成求值复用评估，再决定提取 Purism 算法或增加原生实现。
- 网格创建与调整、变形器绑定、绘制与遮罩编辑均通过正式数据接口完成。
- 参数扫描、多状态观察图、对象定位和必要的几何诊断；执行结果足以支持下一次脚本修正。
- 未完成的多参数组合、范围外规则、缺失关键形态和拓扑变化处理有明确约束，不能静默近似。

完成标准：检查睁眼、半闭、闭眼和区间内状态，Agent 根据数据或图像指出问题并修正；人可以辅助检查，但不负责代做建模或逐次执行脚本。保存重开后保留可编辑结构、参数和形态；修改不是只作用于一张最终截图。

允许先使用带语义名称的图层，不以自动识别任意插画结构作为前置条件。固定生成脚本可以作为配方，但不能冒充 Agent 已具备自主观察和修正能力。

### P3：支持持续的角色制作

**使用任务**：在既有工程上继续制作嘴、眉、头发或其他实际需要的部件，同时维护眼部效果；能够对人提出的局部问题反复调整。

交付内容按真实制作阻碍排序：

- 部件组织、数据增删与重绑定、素材重新导入，保留稳定引用并明确受影响内容。
- 可复用的建模配方和参数命名约定，而不是为每个角色复制一份编辑器代码。
- 角色任务实际需要的多参数组合、修正形态及拓扑与 Keyform 处理；不无依据地泛化。
- 更完善的检查、比较、检查点与可选草稿；人工局部修正复用数据与 Action 接口。
- 基于真实模型规模测量求值、绘制、脚本反馈、历史内存与保存耗时，并针对瓶颈优化。

完成标准：Agent 能读取已有模型后继续工作，不必删除模型重建；局部修正不破坏无关部件。至少有不同输入素材的实际制作记录，证明流程可以复用。此时再依据用途扩展到完整角色，不能只靠增加四边形数量宣称产品可用。

### P4：将创作成果交付给应用

**使用任务**：把实际制作的模型发布给不运行 Editor 的应用，由应用设置参数并持续播放。

交付内容：

- 原生发布数据与资源引用契约，创作工程保存与发布动作分开。
- 独立播放器或宿主接入例子；无需编辑器 Session、历史或脚本任务设施。
- 编辑与播放共享原生求值语义，尽可能复用同一渲染后端；必要的格式转换有明确校验。
- 针对参数端点、区间中点及任务需要的组合状态比较求值数据与实际渲染结果。
- 根据目标应用决定分发平台、加载失败反馈、资源管理及性能要求。

完成标准：真实制作的工程经过发布后可在独立应用中驱动；数据与画面差异在规定容差内；记录实际模型规模和运行环境。不能靠手写另一个模型或导出固定顶点帧代替角色运行时。

P4 的接口约束应在 P2 时就进入设计，并保留最小播放对照，避免最后再重写求值；完整产品交付在该里程碑完成。

## 7. 下一轮实施顺序

下一轮以 P1 为目标，不自动进入旧 Stage 06，也不先做一次覆盖所有模块的大重构。

1. **确定应用与会话边界。** 为正式 Editor 建立入口，将当前模型、预览、历史与脚本运行纳入一个明确 Session；现有样例改为调用正式能力。
2. **提取最小公共绘制接口。** 从原生网格和现有 Cubism drawable 两种输入接入，在现有回归中比较；随后接入真实素材所需的绘制顺序、透明度与遮罩。
3. **打通真实素材与工程管理。** 导入眼部图层，保留画布与位置，提供可用的检查画布、对象信息及保存重开。
4. **接通 Agent 的任务入口。** 在当前会话执行完整脚本，获得状态、结果和对应画面，消除人工反复触发的依赖。
5. **从这份工程进入 P2。** 参数与 Keyform 作为真实制作所缺的产品能力实现，同时评估并复用现有求值算法。

每项实施先列出受影响模块、数据契约、可运行入口、回归与迁移方法，交付后再细化下一项。不在路线图中预先锁死所有类名、目录和函数签名。

## 8. 如何判断进展

一个里程碑完成，必须同时具备：

- **产品证据**：在正式应用、真实工程中完成对应使用任务，并能继续编辑。
- **Agent 证据**：脚本、执行结果和观察记录表明 Agent 能操作并检查，而不只是运行一次预制演示。
- **数据证据**：源数据、求值、保存重开与需要的撤销/恢复符合约定。
- **视觉证据**：真实渲染环境中的多状态检查，明确输入、版本和参数。
- **整合证据**：相关功能进入正式模块，已有模型与工作流没有因迁移而丢失能力。

单元测试和固定样例继续用于回归，但“测试全绿”“支持了一个新类”“多生成一张截图”均不能单独作为产品完成标准。

每次里程碑记录应区分已经实现、实际验证和仍受限的能力。没有性能测量就不承诺性能，没有真实制作记录就不宣称自主建模已经解决。
