# Kasane Editor 分阶段路线图

状态：Stage 00–03 的基础能力保留；Stage 04 已按进程内脚本与可选原生 Action 重新实现，验证结果见交付记录。Stage 05 起为待实施规划。实际实现范围和证据见 [Stage 00–01 交付记录](stages/00-01-delivery.md)、[Stage 02–03 交付记录](stages/02-03-delivery.md) 和 [Stage 04 交付记录](stages/04-delivery.md)。

本文件整理已有讨论中的 Agent-first 编辑器方向，并将第一版拆为逐步可运行、可验收的任务。它定义做什么及何时算完成，不预先规定完整类结构、函数签名和逐文件改动；这些留给各阶段实施文档。

## 1. 最终方向与执行原则

当前目标：Agent 通过应用进程内脚本直接创建、修改 2D 网格、变形器与参数，自行读取数据和实际渲染结果检查、修正，人辅助检查。完成保存与播放链路。普通数据写入不要求事务、不自动生成历史；需要撤销时显式使用 Action。

人工画布编辑属于后续可选能力，不是核心阶段 00–08 的前置条件或验收要求。

不把整个目标作为一个任务。每次只推进一个阶段；每个阶段保留可运行样例，验收通过后再细化下一阶段。文中的子任务也可以分别实施，不要求一次完成整个阶段。

共同约束：

- Document 是常驻内存的创作数据，不等于磁盘文件或 Godot 场景树。
- 固定测试、进程内脚本和可选 Action 共享同一数据接口。脚本可直接写入数据，Action 不构成唯一入口。
- 复用 Godot 的 ClassDB、GDScript 和核心 UndoRedo；不在内核重复实现历史栈。事务是显式操作的可选工具，不强制包裹所有脚本。
- 交互预览不经过保存、导出、重新加载模型的链路。
- 源数据、求值结果、GPU 资源分开；后两者可以重新生成。
- 参数预览值属于会话状态，修改它不等于编辑 Keyform。
- 保存和发布导出是独立动作。
- 第一版使用独立 Godot 应用、C++ 数据内核与进程内 GDScript。
- 第一版不实现 Cubism 工程兼容和 moc3 导出。

核心阶段允许固定视角、固定布局、固定素材、一个对象、同步求值及对象级更新。画布先作为只读预览；缩放、平移、选择、拖点、Gizmo 和工具状态机均不要求实现。不要为了未来能力提前引入通用插件、共享内存、复杂依赖调度或多个独立服务。

- **阶段 03：可保存的模型验证工具。** 固定命令修改、预览、保存重开已形成闭环。

- **阶段 06：最小参数建模器。** 已可做变形与关键形态。
- **阶段 08：受限的第一版产品闭环。** 可审查脚本修改并导出播放。

## 3. 阶段 00：实现内存模型接口

### 目标

直接修改项目代码，新增可复用的内存模型输入与更新接口：不生成或加载 moc3，将内存中的顶点、UV、三角形和纹理送到 Godot，并持续更新。阶段结束时，后续 Document 可以直接调用该接口，不再重新建设预览通路。

本阶段是正式功能交付，不以可行性报告或一次性实验场景作为完成标准。先支持一个纹理三角网格、固定拓扑下的位置更新；此处“内存模型”指最小可渲染数据，不包含参数和变形器求值。

### 子任务

1. 检查现有渲染代码对 `CubismModel` 的依赖，直接实现必要的渲染适配，让内存输入拥有可调用的正式入口。
2. 实现最小创建接口，接受顶点位置、UV、三角形索引和纹理引用；不要求调用方构造 `CubismModel` 或提供模型文件。
3. 实现固定拓扑下的批量顶点位置更新，以及模型清理或释放接口；更新复用已有模型实例和纹理。
4. 明确输入数据的所有权、复制或借用约定、坐标与 UV 约定、调用线程和资源生命周期；校验数组长度、索引范围和数值有效性。
5. 提供固定样例，完全通过上述接口创建纹理四边形、连续更新位置并释放；无需鼠标工具。
6. 添加接口检查与现有 moc3 加载路径的适当回归验证，记录构建和运行方法。

### 交付物与验收

- **代码交付**：可构建、可被后续 Document 调用的创建、更新和释放接口，以及接入 Godot 的实现；接口不能仅存在于演示脚本内部。
- **显示与更新**：调用方提供内存数组与纹理后可显示网格，反复批量更新位置能立即反映在画布上。
- **链路约束**：创建和更新不依赖 moc3，不导出或重载模型文件；纹理可以是预先加载的资源，不要求实现图像导入系统。
- **资源复用**：位置更新不重新创建整个模型或场景，不重复加载纹理；拓扑保持不变时复用可复用的渲染资源。首版允许整块更新该网格顶点，不要求逐字节最小更新。
- **错误与生命周期**：长度不匹配、非法索引或非有限数值明确失败，失败更新保留上一次有效结果；重复创建、更新、释放有可复现的检查，资源引用不会持续累积。
- **回归**：已有 moc3 加载和显示路径仍可使用；提供实际验证方式与结果，若所需本地素材缺失则明确记录未验证项。
- **文档与样例**：接口说明、最小调用样例、构建与运行命令，以及支持范围；验收证据包含实际渲染结果，不能只靠无渲染环境中的逻辑测试。


### 下一阶段入口

阶段 01 必须复用本阶段接口，将 Document 的数据接入它。若需要新增独立的 Godot 渲染适配，可以缩小复用范围，但仍须交付正式的内存接口与代码，不能退回为只证明“Godot 可以画网格”的演示。是否复用 Purism 求值属于后续阶段决定，不阻塞本阶段最小渲染接口。

## 4. 阶段 01：最小内存 Document

### 目标

让场景中的模型由一个明确的数据源驱动，不再由测试代码和 GUI 分散持有。

### 子任务

1. 定义最小 Asset、Mesh 和 Document；先支持一个 Mesh。
2. 确定模型坐标、图像坐标和 UV 约定。
3. 为对象与顶点建立稳定身份；求值或渲染使用连续数组。
4. 用日志或查询结果输出对象摘要，用固定视角画布显示 Document；通过一个批量修改入口更新顶点。
5. 区分文档数据与派生缓存，产生最小的变更集合。

### 交付物与验收

- 最小数据模型说明和固定样例。
- 修改一个顶点后，Document、对象检查结果和画布一致。
- 改对象名称不重建几何资源；改顶点只更新相关网格。
- 原始顶点不被预览或渲染过程覆盖。

### 不做

通用反射框架、完整依赖图、所有未来对象类型、文件格式、复杂停靠面板。

## 5. 阶段 02：最小修改与事务验证

### 目标

通过固定命令可靠地修改一个网格，建立脚本可直接访问、Action 可复用的数据修改语义，不开发人工网格工具。

### 子任务

1. 提供一个测试入口，按显式对象与顶点 ID 批量设置位置。
2. 将一次批量修改作为一个原子操作：验证通过后整体提交，失败则保持原状态。
3. 在显式 Action 中记录修改前后数据，复用 Godot UndoRedo；普通数据写入不记录历史。先不做历史面板。
4. 用固定命令序列展示“修改 → 预览 → 撤销 → 重做”，并覆盖取消未提交修改。

### 交付物与验收

- 一组可运行的固定命令或测试用例，以及只读预览结果。
- 一个显式 Action 只产生一个 Undo 步骤；撤销和重做恢复正确数据。普通批量写入可以不进入历史。
- 无效批量修改整体失败，不留下部分结果；取消未提交修改不改变 Document。
- 更新只经过内存修改入口，不依赖保存或重新加载模型。
- 此阶段仅验证短事务，不要求长生命周期 Agent 草稿、完整命令框架或 GUI 工具状态机。

### 不做

缩放、平移、顶点选择与拖动、框选、Gizmo、工具栏、历史面板、通用网格拓扑工具、自动铺点、吸附、镜像。

## 6. 阶段 03：保存与重开

### 目标

证明固定命令修改的 Document 可以持久化，并在下次打开时继续使用。

### 子任务

1. 定义最小带版本号的项目格式和资源引用方式。
2. 保存 Document；打开项目后重建求值与渲染缓存。
3. 明确未保存状态、资源缺失及不支持版本的提示。
4. 使用安全替换方式保存，避免失败破坏上一次成功文件。

### 交付物与验收

- 项目格式说明及可重开的样例项目。
- 固定命令修改、保存、关闭、重开后，ID、坐标、UV 和纹理对应关系保持一致；通过测试入口指定路径即可，不要求文件对话框。
- 保存不依赖把画布结果反写到源数据。
- 失败保存保留原项目；不支持的格式版本明确拒绝。

### 不做

发布用格式、压缩打包、完整迁移框架、跨会话 Undo 历史、云同步、自动保存系统。

## 7. 阶段 04：进程内脚本与自检基础

### 目标

Agent 编写的脚本在应用进程内直接访问当前 Document，自行读取数据和画面检查结果。人辅助检查，不要求每次修改都人工批准。

### 子任务

1. 提供进程内 GDScript 宿主，运行脚本时传入当前文档；脚本更新不重载模型。
2. 通过 ClassDB 暴露网格对象、属性、稳定 ID 查询和批量几何访问。
3. 支持直接改名、位置修改、创建与几何替换，不强制事务或历史。
4. 显式 Action 复用 Godot UndoRedo，可选事务提供原子批次；不维护第二套历史栈。
5. 提供对象检查、预览读取及对应明确 revision 的实际渲染图片，作为 Agent 自检基础。

### 交付物与验收

- 进程内脚本宿主、对象 API、直接编辑与显式 Action 示例。
- 脚本直接修改当前 Document，立即同步预览；不自动生成 Undo。
- 显式 Action 可以包含创建、改名和几何修改，并整体撤销、重做；失败时恢复文档。
- 普通脚本失败时允许保留已经完成的直接修改，不能暗中包裹事务。
- 重开项目后旧对象句柄与旧 Action 状态失效，revision 不重复。
- 数组访问的复制/写回约定明确，批量操作不经过逐顶点 RPC。
- 自检可以获得源数据、当前预览和实际渲染图；headless 无渲染环境不能代替截图。

### 边界

当前数据 API 要求每次提交的几何有效；暂不提供裸 C++ 内存视图或暂存无效拓扑。Action 辅助类首版采用整个文档快照，其撤销可能覆盖后续直接写入；也可直接使用 Godot 属性 Action。自动化审美判断与完整自主建模能力由后续变形、参数和真实部件阶段继续验证。


## 8. 阶段 05：变形器

### 目标

建立“源数据 → 变形求值 → 画布”的最小工作链路。

### 子任务

1. 先完成 Rotation：创建、绑定、修改、求值与撤销。
2. 再完成固定网格规格的 Warp：通过进程内脚本创建、批量设置控制点、求值。
3. 加入有限的父子嵌套，区分组织关系和变形父节点。
4. 通过数据 API 完成修改，固定视角画布显示结果；保存格式加入这些数据，不要求控制点编辑工具。
5. 按对象记录依赖和失效范围，不引入通用调度框架。

### 交付物与验收

- 一个 Rotation + Warp + Mesh 的样例。
- 改变控制点或旋转角度立即更新预览，不改变 Mesh 原始顶点。
- 明确局部坐标及变形应用顺序；内核测试入口与进程内脚本的相同操作得到相同结果。
- 循环父子关系被拒绝；修改、撤销、保存重开都成立。

### 不做

自动拟合复杂结构、任意最终姿态反求源顶点、复杂变形器类型、完整 Cubism 求值兼容。

### 待实施文档决定

求值代码从现有实现提取还是先实现受限原生子集，依据阶段 00 结论决定，并明确支持范围。

## 9. 阶段 06：参数与 Keyform

### 目标

让一个部件能在几个明确编辑的形态之间连续变化。

### 子任务

1. 创建参数范围、默认值、属性绑定和三个 Keyform。
2. 先完成一种目标属性，例如 Warp 控制点位置；再按需要扩展到 Mesh 位置与 Rotation 角度。
3. 实现单参数插值，明确范围外处理、默认值及缺失关键形态的规则。
4. 在 API 中显式区分基础形态写入、指定 Keyform 写入和只读参数预览；固定画布展示当前参数与目标信息，不要求形态编辑面板。
5. 增加脚本对象 API 能力、保存支持及参数依赖的缓存失效。

### 交付物与验收

- 一个脚本写入三个形态、自动扫描参数并显示结果的样例。
- 设置预览参数不修改 Document、不增加 Undo；写入 Keyform 才算文档修改。参数滑条可选，不作为验收条件。
- 关键点、区间中点、最小值与最大值的结果符合定义。
- 扫描预览参数不导出文件、不重建整个模型；未受影响的独立对象不必重新求值。
- 保存重开后的求值结果与脚本写入后的一致。

### 范围限制

- 每个被驱动属性只绑定一个参数；不同层级对象可以各自被不同参数控制。
- 已绑定关键形态的几何暂不允许改变拓扑，明确返回原因。
- 写入 Keyform 必须显式指定目标关键值，不根据当前预览参数隐式选择附近形态。

### 不做

同一属性的多参数组合、自动头部转向、拓扑与 Keyform 自动迁移、动作时间轴。

## 10. 阶段 07：Agent 草稿与可审查反馈

### 目标

在直接修改之外提供可选草稿，Agent 可自行检查、接受或拒绝，人也可辅助检查。人工确认不是每次建模的前提。

### 子任务

1. 基于明确 revision 创建草稿，复用未修改的资源，按对象或数据块复制修改内容。
2. 将阶段 04 的编辑操作用于草稿，不新增另一套编辑语义。
3. 提供结构化变更摘要、诊断和指定参数状态的图片预览。
4. 提供整体接受、拒绝、取消；接受时检查主文档 revision。
5. 将一次接受记录为一个 Undo 步骤。

### 交付物与验收

- 一次脚本提案从执行、检查到接受或拒绝的完整样例。
- 未接受的修改不改变主文档；主视图与草稿视图的缓存不会混用。
- 预览对应明确的草稿版本和参数值，不能返回旧帧冒充最新结果。
- 拒绝或脚本失败后主文档不变；接受后可以撤销和重做。
- 另一脚本或测试命令修改主文档后，旧草稿不能直接覆盖。

### 边界

审查可通过结构化报告、图片及显式 accept/reject 调用完成，专用审查面板不是验收前提。先从运行中的 Editor 获得图片；独立无界面渲染服务不作为本阶段前置条件。截图必须使用实际启用渲染的环境，不能把 Godot 的无渲染 headless 模式当作截图实现。

### 不做

局部接受、自动 Rebase、并行 Agent 协作、语义合并、内置对话产品。

## 11. 阶段 08：真实部件与独立播放

### 目标

证明已完成的能力可以组合成一个实际部件，并且脱离 Editor 仍能播放。

### 子任务

1. 导入一组自有或许可明确的眼部 PNG，支持原画画布尺寸和图层位置。
2. 按样例需要加入多 Mesh、基础绘制顺序、透明度和简单蒙版；逐项实现，不泛化为完整材质系统。
3. 用进程内脚本和固定素材完成眼白、虹膜、眼皮的组织、变形和睁眼参数，通过只读预览检查。
4. 定义受限的原生发布数据，导出后由一个独立测试播放器加载。
5. Editor 与播放器共享求值语义和渲染适配，在相同参数下比较结果。

### 交付物与验收

- 可编辑项目、构建脚本或操作说明、导出文件及播放器样例。
- 脚本创建、脚本修正、视觉检查、提案审查、保存重开、导出播放的链路完整；不依赖人工拖点。
- 端点和中间参数状态都接受检查，不能只验证闭眼和睁眼两张图。
- 编辑与播放的几何数据在定义的容差内一致；截图比较使用相同环境及明确容差。
- 记录实际模型规模、测试机器、参数更新反馈及脚本预览耗时，不在缺少测量时宣称性能达标。

### 拆分执行建议

本阶段分别编写或依次实施“多图层显示”“眼部样例”“导出与播放”三个任务，避免成为一次大集成。

### 不做

全身角色制作、自动高质量眨眼、PSD、物理、动画、所有混合模式或 Cubism 文件兼容。

## 12. 可选后续阶段 H：人工画布编辑

此阶段不在核心 00–08 的依赖链上。等流程走通、实际使用证明需要手工修正时，再决定是否实施及支持范围；允许不做。

建议每次只选择一个小能力：

1. 只读视图缩放与平移。
2. 顶点选择与高亮，不修改模型。
3. 单个顶点拖动，复用已有事务与 Undo；松手提交、Escape 取消。
4. 确有需要时再加入多选、框选、变形器控制柄及 Keyform 编辑界面。

验收重点是复用已有文档修改语义，而不是另建一套 GUI 数据模型。实施前需明确编辑基础数据还是某个 Keyform，以及坐标转换规则。

## 13. 如何编写各阶段实施文档

使用 [实施文档模板](IMPLEMENTATION_TEMPLATE.md)。进入一个阶段时再确定：

- 已完成阶段提供了哪些真实接口和限制。
- 本阶段必须新增哪些数据、编辑命令和最小 UI。
- 修改哪些现有文件，哪些内容可以复用。
- 每个子任务如何单独运行、展示和验收。
- 错误、撤销、缓存失效和保存语义如何处理。
- 尚未确定的问题需要什么最小实验，而不是先抽象出通用方案。

只有当实际证据改变前提时才调整路线图。新增需求应归入明确阶段或后续范围，不默默进入当前任务。
