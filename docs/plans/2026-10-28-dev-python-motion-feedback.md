# dev-python 模型读取与 Motion 制作反馈

日期：2026-10-28。状态：使用反馈与改进建议，未实施 API 修复。

本轮通过 `./tools/dev-python` 连接现有 Editor，读取模型结构，新增简单动画，
随后制作画心、爆炸、懊恼和恢复的剧情动画。连接、分页读取、候选编辑、Preview、
GPU 渲染、提交和正式读回均完成。主要改进方向是复杂工作流示例、观察与播放语义、
预算诊断，以及曲线构造便利性。

本记录区分实际异常、待定位的现象、易用性建议和调用者错误。
读取过 `zipzi-python2` 源码、测试和相关文档，不能据此判断公开帮助无法独立完成任务。
未检查 Runtime 或 Editor 内部实现，未定位宿主调度或渲染根因。

## 完成范围与验证边界

| 任务 | 实际结果 | 验证范围 |
| --- | --- | --- |
| Editor 连接和结构读取 | 成功 attach 唯一 resident Session；列出 260 个网格、128 个参数、175 个 transform | 使用分页、参数批量读取与 Source 一致性检查；没有修改模型 |
| 轻柔问候 | 新增 6 秒、30 FPS、15 条参数轨道的 Motion | 候选 CPU 播放采样、提交和正式读回；没有进行视觉验收 |
| 心形魔法失控 | 新增 13 秒、30 FPS、132 条轨道的 Motion | 两版视觉草稿，最终版渲染检查 11 个时刻；提交后 Clip 和注册项读回一致 |

剧情动画复用模型已有 `special_02` 的画心、魔法棒和爆炸曲线，重新配置开心及懊恼表情，
并增加恢复段。它验证了复杂动画的改编流程，不代表从零设计魔法棒轨迹已通过验证。
原动画保留；新增动画只提交到 resident Session，本轮未保存项目到磁盘。

不同阶段的 Runtime 身份发生过变化，不能把全部连接观察归为同一个宿主进程的连续行为。
最终剧情动画提交回执对应 SDK `generation=2, revision=4`；SDK 版本内的 session 标识
与 Runtime Session serial 属于不同身份域，不应混用。

## 问题与建议

### 连接恢复示例应覆盖 attach 超时

**实际现象：**简单 Motion 制作前，握手和 `sessions.list()` 成功，随后
`sessions.attach()` 在默认请求超时内没有收到回复，抛出 `OutcomeUnknown: timed out`。
当前 `connect()` 默认 `timeout=10.`，其语义是每次请求的 socket 超时。
首次脚本没有在进程内恢复该调用，退出时又出现 Runtime 清理提示，要求先恢复原请求
或显式放弃 pending 请求。后续新客户端使用更长超时和 `recover_call` 后成功继续。

这不是已确认的 attach 实现缺陷，也不能据此认定调大超时解决了根因。
第一次进程退出后没有恢复原调用；后续成功连接不等于恢复了第一次调用。

**建议：**提供覆盖 connect、list、attach、`OutcomeUnknown`、继续恢复和最终清理的完整示例。
诊断信息应便于关联操作名、请求身份、超时配置和宿主身份；先核对现有结构化错误字段，
再确定需要新增哪些信息。超时后应恢复原请求，尤其不能将同样的写操作当作新请求重发。

**验收方向：**模拟 attach 丢失回复；确认原调用恢复后得到 Session，清理行为明确，
不会用重放创建另一份业务操作。真实 Editor 超时排查另需宿主日志和请求时间记录。

### 直接观察与动画 Preview 的适用语义需要更容易发现

**实际现象：**对该模型执行默认参数的 `modeling.observe()`，画面同时显示了多套手臂。
使用现有 Motion 的 Preview 后，演出显示为正常的两只手臂。
制作新 Motion 时保留了原有手臂部件显隐轨道。

默认参数不一定构成适合展示的演出姿态。此现象不能直接判定为 Pose 或观察接口错误；
本轮没有隔离 Part opacity 轨道、Pose 设置和参数状态各自的作用。

**建议：**在公开指南中并列说明：显式参数姿态观察、动画 Preview、Editor 当前播放状态
分别包含哪些输入，哪些状态独立，以及如何处理多套手臂等模型特有的部件选择。
提供包含 Part opacity 轨道的最小示例，不隐式替调用者挑选模型姿态。

**验收方向：**在同一 Source 下，对比默认参数、明确的部件选择和含相关轨道的 Preview；
解释可见差异，并证明独立 Preview 不改变人的 Editor 播放。

### 部分批量观察帧身体缺失需要独立定位

**实际现象：**初次九姿态 `modeling.observe()` 批量渲染中，默认帧身体完整，
部分心形和表情姿态帧只显示局部对象。后续 Motion Preview 的关键帧渲染未观察到同样问题。

这是值得排查的视觉现象，尚不是已确认的 GPU 批量渲染缺陷。
两种路径的参数与部件状态不同，没有完成相同姿态的单帧和批量对照。
不能从 Preview 成功推出底层原因，也不能认定属于掩码缓存或资源复用错误。

**建议及验收方向：**使用冻结的同一 Source，将完全相同的姿态分别放入单帧请求、
批量首帧和批量后续帧；比较 RGBA、alpha、部件显隐及观察 manifest，
保留构建身份与 GPU 信息。如果重复姿态仍出现像素差异，再进入实现层排查。

### 采样预算错误应更便于调整请求

**实际现象：**一次请求 11 帧、每帧 1000×1100 的候选 Preview GPU 输出，被拒绝并报告
`Runtime budget exceeded: accounted CPU bytes`。
之后改成每批最多 3 帧、850×950，逐批等待并释放 Job，成功输出 11 个时刻。

本轮同时改变了批量大小、分辨率和结果持有方式，不能据此确定哪个变量单独解决问题，
也不能把 3 帧当作通用安全上限。`sample()` 接受 1..64 个时刻，不代表任意模型和分辨率
下都能获准执行。预算拒绝本身属于预期保护行为。

**建议：**检查现有 `limits()` 和错误字段能否解释本次拒绝；若不足，提供本次估算、
当前计费额度、适用上限及主要占用类别。文档补充分批采样、Job 释放和恢复缓存的关系。
自动拆分若作为便利层，应明确 Source、结果顺序、失败边界和 Preview 已完成 seek 的状态，
不能无提示地改变原批量调用的契约。

**验收方向：**固定模型，分别改变帧数和分辨率；确认拒绝发生在预算约定的阶段，
错误可指导调整，且分批结果与允许执行的同姿态请求一致。

### 复杂 Motion 构造需要更少的机械代码

**实际体验：**创建 Motion 需要显式 Clip ID、注册项 ID 和目标容器；随后读取默认 Clip，
用 `replace` 配置 Track、Key、Segment 等值。复制原动画时，需要重建新轨道和关键帧身份，
再追加恢复段、调整轨道顺序和事件。现有类型能表达这些工作，但临时脚本较长。

**建议：**优先补充完整示例，再考虑关键帧曲线构造、平滑插值、轨道复制及追加片段的
便利操作。先审查已有 duplicate 操作的适用范围；本轮手动复制不能证明 API 缺少复制能力。
任何辅助操作都应明确身份分配、插值约定、时间单位及已有字段的保留规则。

**验收方向：**用公共入口完成“复制已有动作、修改表情、追加恢复段、候选渲染、提交读回”，
并验证新旧动画独立、身份符合契约、原动画不变。

### 语义发现与表情叠加需要工作流支持

**实际体验：**变形器从 `scene.list()` 筛选 `object_kind == "transform"`；摘要未直接区分
Warp 和 Rotation。参数通过分页及完整值读取后，在客户端建立 Runtime ID 查找表。
心形绘制、显隐、颜色、缩放、蓄光和爆炸的编排关系，则通过原动画和渲染理解。

第一版剧情动画保留了原来的元音轨道，开心阶段视觉上仍偏惊讶。
第二版清零相关圆嘴元音，配置宽嘴笑和笑眼，渲染后才确认开心表情明显。
这是制作中的视觉迭代，不能归因于 API 计算错误。

**建议：**改善变形器入口及子类型导航，提供按 Runtime ID 建立查询索引的示例；
若增加便捷查询，应说明空 ID、重复 ID 和缺失结果的处理。
复杂动画指南应包含同一表情受多个通道共同影响的例子，强调关键帧数值通过不能代替视觉验收。
模型特有的参数依赖可作为显式元数据扩展讨论，不应依赖名称猜测自动生效。

### 浮点读回与对象相等的约定应明确

**实际现象：**简单 Motion 首次候选写入后，完整 Clip 的严格相等断言失败；
之后改为核对目标、轨道和关键帧，并对时间与数值使用容差，采样及提交验证通过。
没有记录具体差异字段，不能确定严格相等失败全部由浮点精度造成。

**建议：**明确各类动画数值的存储精度、规范化规则，以及 DTO 相等是否适合判断语义一致。
示例中分别检查身份、结构、容差数值和播放结果；若增加差异诊断，返回具体字段路径。

**验收方向：**构造含不能被目标精度精确表示的小数的最小 Clip，保存请求值和读回值，
逐字段说明差异来源，不用放宽比较掩盖轨道丢失、排序或身份变化。

## 调用者错误与流程不足

以下事项不应登记为 SDK 功能缺陷：

- 结构读取脚本的 JSON 转换漏处理容器，导致序列化失败；之后又将大量结果打印到终端，
  输出被截断，改成文件导出才完成交付。这造成了额外读取。
- 根据猜测访问了不存在的源码文件名；没有证据表明公开目录无法发现对应接口。
- 首次 GPU 探测漏传 `ObservationView.roi`，触发必填参数错误。
- 预算拒绝后的清理代码误用 `EditState.OPEN`，实际公开枚举为 `EditState.editing`。
  第二个异常干扰了原始错误展示，应查明状态契约并保留原异常。
- 首次 attach 超时后，脚本退出前没有恢复原请求，导致清理提示。
- 第一段简单动画只做参数采样，缺少视觉验收；后续剧情动画才实际检查渲染图。
- 将整个 Clip 的精确相等作为第一轮唯一验证标准，失败时又没有保存字段差异。

`dev-python` 每次准备环境会输出较多编译警告，确实干扰阅读；但 warning 本身不等于运行失败。
复杂任务中将构建 stderr 和业务结果分别保存即可缓解。
若增加日志选项，应保留构建失败的退出状态和诊断，避免以隐藏警告代替解决问题。

## 建议优先级

以下是后续工作的建议顺序，不是已确认缺陷的严重性评级。

| 优先级 | 工作项 | 预期结果 |
| --- | --- | --- |
| 高 | 同姿态单帧与批量观察对照 | 判断身体缺失是否可复现，以及是否属于实现问题 |
| 高 | Editor 超时与恢复示例，补齐宿主诊断证据 | 避免未知结果被重放，缩小真实超时原因 |
| 高 | 预算诊断与复杂模型分批采样示例 | 让调用者能有依据地缩小请求 |
| 中 | 完整视觉 Motion 示例 | 覆盖参数发现、部件选择、表情叠加、候选检查与恢复段 |
| 中 | 自动取景便利层 | 基于显式 bounds 选择构造 ROI，保留固定镜头和 padding 控制 |
| 中 | 曲线复制和构造示例或辅助操作 | 降低机械身份和控制点代码量 |
| 中 | 数值精度与差异诊断 | 区分规范化和真实内容变化 |
| 低 | 变形器子类型、Runtime ID 查询便利性及日志体验 | 减少导航和结果整理成本 |
