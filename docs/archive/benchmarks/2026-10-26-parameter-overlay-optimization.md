# 参数拖动辅助层：CPU 优化与验证 — 2026-10-26

> **呈现指标更正：** 后续复核发现，旧版报告按 Metal 纹理地址关联模型帧，会把复用该地址的辅助层纹理误认成旧模型帧。因此下文涉及模型帧率及其关联延迟的结论已撤回，保留原始数据供审计；独立 CPU 分段、工作次数和全部窗口绘制时间仍有效。修正与复测见[更正报告](2026-10-26-selected-ui-release-recheck.md)。

恢复 CB27U1 4K/120 Hz 显示环境后，已完成优化前后的原生窗口配对复测。**开发构建全选显示顶点时，新预览呈现频率从 31.89 Hz 提升到 45.47 Hz（+42.6%），输入到呈现 P95 从 62.98 ms 降到 54.01 ms。** 三轮方向一致；全选但跳过绘制从 35.94 Hz 提升到 53.95 Hz。

改善主要来自已实现的 CPU 优化。有效显示环境下，可编辑性重建 P95 从开发构建的 10.08 ms 降至 2.12 ms，Release 从 1.48 ms 降至 0.37 ms。100 个针对性测试此前已通过，本次没有再改产品源码或重编译。

**本次不能称为所有场景的整体性能提升。** 开发构建全选仍明显慢于未选中，单帧 UI draw P95 没有下降；Release 默认输入相位的全选组三轮中位数从 116.36 Hz 降到 110.00 Hz。补充相位对照显示双方都有较大呈现节奏波动，未确认稳定的 Release 帧率收益，默认组的下降和延迟变化均保留。

## 实现

1. `CanvasScene` 保存一份该姿态的 `Arc<PreviewValues>`。场景本来就需要参数表计算 Glue，现在将其同时供 Mesh、Deformer 的编辑能力查询使用。相同参数的几何/外观更新和场景克隆共享该表；参数变化时创建新表，旧帧保留自己的参数。
2. `ControlEdit::describe` 同时返回可编辑描述和 Mesh 拖动权重，删除后续重复的 `mesh_drag_weight` 查询。没有活动 BlendShape 绑定的 Mesh 提前返回；普通关键形匹配也复用参数表。
3. `canvas_notice` 只查询限制信息并复用可编辑状态，不构造顶点、边和控制器图形。`canvas_hover_hint` 同样直接查询命中的组件或手柄。隔离范围、锁定、关键形外提示和 Glue 受限点的规则保留。

未修改 Metal 绘制机制、默认构建优化级别或参数更新频率。

## 恢复显示后的原生窗口复测

使用此前保存并核对 SHA-256 的四份 before/after、dev/release 二进制，避免工作区后续变化影响配对。仍使用同一份 `mao_pro.zipzi` 副本、Angle_X、150 个选中 Mesh、5,159 个顶点、12,202 条边和 941×1312 物理像素预览。环境为 Apple M4、16 GiB、macOS 27.0.1、CB27U1 3840×2160／逻辑 1920×1080／120 Hz。

每进程 30 次预热、360 次正式输入，目标 120 Hz。未选中、全选显示、全选但跳过绘制三种状态，各运行三轮 before/after 配对；第二轮反转构建和条件顺序。36 个正式进程关闭详细计时，四个详细进程另行归因。下表为三个进程各自指标的中位数，不合并原始样本；时间单位 ms。新预览 Hz 使用新模型纹理的实际呈现时间戳，不能用窗口合成 Hz 替代。

| 构建与状态 | 新预览 Hz：前 → 后 | UI draw P95：前 → 后 | 输入到呈现 P95：前 → 后 |
| --- | ---: | ---: | ---: |
| 开发，未选中 | 115.05 → 106.63 | 3.840 → 3.961 | 48.860 → 47.945 |
| 开发，全选显示 | **31.89 → 45.47** | 9.697 → 9.990 | **62.983 → 54.010** |
| 开发，全选但跳过绘制 | **35.94 → 53.95** | 7.973 → 8.561 | 57.767 → 48.960 |
| Release，未选中 | 118.33 → 118.33 | 3.811 → 3.865 | 34.491 → 34.495 |
| Release，全选显示 | 116.36 → 110.00 | 5.216 → 5.297 | 45.051 → 48.029 |
| Release，全选但跳过绘制 | 105.37 → 118.33 | 4.348 → 4.335 | 45.799 → 34.105 |

开发构建全选时的逐轮结果：

| 轮 | 优化前 Hz | 优化后 Hz |
| --- | ---: | ---: |
| 1 | 32.16 | 46.35 |

开发全选组改善稳定，而未选中组和 Release 的逐轮波动较大。例如开发未选中组，优化前三轮为 99.84／117.67／115.05 Hz，优化后为 118.33／106.63／99.39 Hz；不能把该组中位数 −7.3% 直接归因于新增 CPU 工作。所有逐轮数据和终态保留在 JSON。

有效显示下，开发全选 UI draw P95 仍约 10 ms，比优化前高约 3%，没有证明单帧绘制更快。窗口呈现从约 61.9 Hz 增至约 89.6 Hz，但新模型纹理仅从 31.9 Hz 增至 45.5 Hz；每次新预览仍伴随接近两次窗口绘制。这些残留工作解释了为何 CPU 热点下降约 79%，不能等比例换算为帧率提升；它们是下一轮应继续拆分的对象。

### Release 输入起始相位诊断

默认组 Release 全选出现 −5.5% 的中位数差异，因此补充了相对上一次呈现时间戳的 0／2,500／5,000 μs 输入起始相位，各两轮，反转相位和版本顺序。此设置对齐起始时刻，后续调度仍有抖动，不是持续硬锁相。这 12 个诊断进程不替代默认组三轮结果。

| 起始相位 / μs | 优化前新预览 Hz（两次） | 优化后新预览 Hz（两次） |
| --- | --- | --- |
| 0 | 118.00／117.66 | 118.00／117.99 |
| 2,500 | 101.68／111.64 | 104.71／107.30 |
| 5,000 | 116.01／118.33 | 118.33／117.67 |

相位诊断中，同相位的帧率差异没有形成稳定的退化方向，但同样没有证明 Release 整体收益。部分进程的输入到呈现延迟相差约一个刷新周期；例如 0 μs 第一轮为 40.60 → 48.52 ms，第二轮为 40.61 → 40.62 ms。第一轮较慢的 after 进程里，模型交付延迟约 40% 与 drawable 等待区间重叠。这支持呈现和调度节奏会影响结果，仍不足以单独证明所有差异由相位造成。

新增回归验证覆盖：

- 同一姿态的克隆和不变参数更新复用参数表；新参数表不覆盖保留帧中的值。
- 同一 Mesh 的描述和拖动权重合计只调用一次 BlendShape 查询；提示随后由画布复用，不重复构建能力缓存。
- 提示和悬停查询不会调用完整 overlay 构建；关键形外仍显示正确的受限顶点和悬停说明，锁定/撤销仍更新状态。
- BlendShape 权重随约束变化；弱影响拒绝编辑；中性样本允许编辑普通关键形；保留帧仍使用自己的有效权重。

## 先前关屏环境的 CPU 分段复核

使用与[上一轮](2026-10-26-parameter-overlays.md)相同的 `mao_pro.zipzi` 磁盘副本、Angle_X、150 个选中 Mesh、5,159 个顶点和 12,202 条网格边。每进程 30 次预热和 360 次正式输入，目标 120 Hz。保存优化前后 dev/release 二进制，全部构建完成后才测量，四个 CPU 进程未检测到编译器干扰。参数在每个进程中实际改变 93 个 Mesh。

表中是 UI 线程工作段的墙钟 P95，单位 ms；每格只有一个详细进程，属于归因复核，不替代三轮原生呈现性能验收。嵌套阶段的 P95 不相加。

| 阶段 | 开发：优化前 | 开发：优化后 | Release：优化前 | Release：优化后 |
| --- | ---: | ---: | ---: | ---: |
| 可编辑性重建 `overlay.access_build` | 9.782 | 1.987 | 1.423 | 0.346 |
| 其中 Mesh BlendShape 目标查询聚合 | 8.115 | 0.349 | 1.151 | 0.045 |
| 状态提示查询（含必要的能力重建） | 10.860 | 2.171 | 1.562 | 0.375 |

开发复核中，每次能力重建的 Mesh BlendShape 查询从约 268 次降为 **150 次**；可编辑状态查询过程中不再反复构建全部参数的 HashMap。状态提示的 `overlay.total`、顶点和控制器生成阶段已消失，完整几何只由画布请求生成。

先前关屏环境中，原始 UI draw P95 并没有同步下降：开发从 8.391 ms 变为 10.331 ms，Release 从 4.848 ms 变为 5.652 ms。开发构建测量区间内 draw 次数也从 584 变为 293，更新与合成节奏发生变化；因为呈现全部被丢弃，不能据此确认正常显示下的整体收益或回归。该现象保留在原始数据中；现在已补齐上面的有效呈现环境交错配对测试，但仍没有证明单帧 UI draw 改善。

## 数据完整性与结论边界

- 恢复显示后共 52 个有效进程：36 个正式配对、4 个详细归因、12 个起始相位诊断，共 18,720 次正式输入。结束标记完整，丢失事件为 0，所有有效进程均无编译器干扰。
- Release 的报告 issues 为空；开发进程只保留预期的 debug 构建提示。每个进程实际改变 93 个 Mesh，所有请求终态均保留，没有只筛选已呈现请求。
- 相位诊断曾有一个进程检测到短暂 Xcode 编译，已排除并重测，原始数据保存在 `interfered-phase-2500-round-1-before-release/`。第一次关屏导致没有呈现时间戳的完整测试保存在 `invalid-closed-display-before-dev-unselected/`。
- 先前四个关屏 CPU 进程另计 1,440 次输入，保留缺失呈现时间戳的 issues 和 `fps_usable=false`，不合并进当前帧率数据。
- 确认的收益是开发构建全选时的新预览吞吐和 CPU 热点改善；Release 的稳定整体收益及更广模型、参数、视口尺寸尚未建立。单帧 UI draw 和接近两次窗口绘制/新预览的残留工作仍需后续优化。
- 本次没有新增产品源码变更；沿用此前通过的 100 个针对性测试。自动输入从 GPUI 分发开始，不包含硬件/OS 输入送达和屏幕像素响应；输入到呈现不等同于 input-to-photon。
