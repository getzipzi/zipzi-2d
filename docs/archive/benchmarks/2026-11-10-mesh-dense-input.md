# Mesh 密集输入限流实验

保留首个移动立即执行、后续只取最新样本的方案作为 [密集输入样板](../../plans/dense-input-scheduling.md)。用户用该实验版在 Windows 实际拖动，反馈明显优于不限流。自动对照显示更新间隔缩短，提交延迟和提交时位置差的变化则因场景而异。

## 测量条件

Windows、RTX 5060、Mao 的同一 158 顶点 Mesh，视口 1061 × 1478 物理像素。每种选择热身 30 个输入、测量 360 个输入。普通和密集模式采用同一墙钟轨迹，横向每秒两个周期。密集模式每次唤醒注入四个移动事件。两侧都使用原生 D3D11 和绘制前取用后台帧。每个对照在各自同一 Release 二进制上交替运行，每场景每侧两次，共八个进程。检查编辑、最终画布和 Undo，编译与测量分开。

P95 取每个进程 P95 的中位数。延迟止于 CPU 平台绘制返回。位置差估计的是提交时的逻辑像素距离，未计入旧姿态在两次更新之间的停留。四事件突发提供合成压力，实际鼠标投递和显示扫描需要单独测量。

比较时使用 `ZIPZI_MESH_MOVE_COALESCE=0/2`，二进制 SHA-256 为 `18f244720b77733dc6a7f1f3526a042df1baa1ff4d3c419a8dc05a87bf924da9`。样板仍由 `=2` 启用。提交整理时去掉了纯等待模式，明确回调归属，并保留了拖动起步和 Shift 锁轴的事件顺序。表格保留原实验版测量。

整理后的样板通过 20 项启用态画布测试。专门的调度回归验证起步阈值、首次有效移动、每帧的最新样本和松手前已排队的移动。启用 `ZIPZI_MESH_MOVE_COALESCE=2` 后，用 `cargo test --locked -p zipzi-editor --lib --features test-support leading_mesh_drag_runs_first_move_and_flushes_latest_only -- --ignored` 运行该测试。

## 淘汰的纯等待方案

这种方案把首个移动也推迟到下一帧。密集更新变得均匀，但提交延迟和位置落后增加。结果来自独立的一轮 0/1 对照，不能与上表当作同一配对。

| 场景 | 请求 / 输入，默认 → 纯等待 | 提交延迟 P95，ms | 更新间隔 P95，ms | 位置差 P95，逻辑 px |
|---|---:|---:|---:|---:|
| 普通单点 | 720/720 → 682/720 | 17.16 → 17.28 | 18.90 → 17.79 | 42.93 → 43.71 |
| 普通八点 | 720/720 → 679/720 | 16.79 → 17.21 | 18.48 → 17.60 | 42.16 → 44.12 |
| 密集单点 | 720/720 → 171/720 | 13.65 → 17.23 | 32.68 → 17.67 | 30.25 → 42.03 |
| 密集八点 | 720/720 → 171/720 | 14.95 → 16.96 | 32.94 → 17.72 | 29.36 → 44.35 |

比较用二进制 SHA-256 为 `3ea99bb0e9b5d5c7b2995343bee21c563c80be8a1501b2531399bc58df612873`。最初有一次试跑因旧基准要求每个输入同步求值而退出。有效对照的基准检查已改为要求每个输入实际求值或有明确待处理项，并核对最终画布和 Undo。

最初的大幅拖动压力基线及原始 trace 在本机 `target/mesh-drag-stress/`。两种限流的原始 trace、环境和每轮汇总分别位于 `target/mesh-follow-pointer/leading-frame/` 与 `target/mesh-follow-pointer/coalesce-v2-frame/`。现行运行方式见 [Windows 基准指南](../../../tools/benchmarks/README.md#windows-gpui-cpu-and-image-upload-diagnosis)。
