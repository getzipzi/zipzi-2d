# 全选 UI 优化：Release 复核与呈现关联更正 — 2026-10-26

修正模型帧关联后，三轮 Release 对照中，两项优化同时开启的新预览呈现频率均为 **117–119 Hz**；进程指标中位数为 **112.62 → 118.67 Hz（+5.4%）**，全部窗口绘制的 UI draw P95 为 **4.993 → 4.599 ms（−7.9%）**。本组没有复现稳定的 Release 回退，保留菜单缓存和等待新帧再刷新画布两项优化。

此前报告按 Metal 纹理地址关联模型帧存在错误，**旧的模型帧率及其关联延迟结论已撤回**，包括先前约 5% 的 Release 下降和开发版 +23% 的帧率数字。独立 CPU 分段、调用次数、全部窗口绘制耗时不依赖这个关联，仍然有效。

## 发现的测量错误

`frame-trace-report.py` 原来将 `compose_surface.texture` 地址关联至这个地址最近一次 `published` 的模型请求。但模型纹理释放后，其地址可能被辅助线或顶点纹理复用；后者没有模型 `published` 事件，报告就误将辅助层的合成当成旧模型帧的呈现。

一个明确反例来自修复前 `ablation-round-2-combined`：同一张窗口图像只有一个模型视口、三个 Metal surface，却被关联到模型请求 **3103、2933、2713**。请求 2713 被算出 653.96 ms 的 UI 等待，实际匹配的是复用了地址的辅助层。该进程 935 次有模型地址匹配的合成中有 870 次被错误匹配到多个模型请求。

这种误关联会将本来未合成的旧模型请求算成后来呈现，污染终态、延迟和新预览频率；因此不能仅删掉长延迟异常值，也不能继续使用旧的帧率差异。此前三份归档已增加撤回说明，原始数据保留供审计：

- [最初的辅助层归因](2026-10-26-parameter-overlays.md)
- [第一轮 CPU 优化](2026-10-26-parameter-overlay-optimization.md)
- [重复画布和菜单开销优化](2026-10-26-selected-ui-optimization.md)

## 关联修复

- `preview.rs` 在启用 frame trace 时，把请求 ID 写入该帧 Metal 资源的 label；模型渲染器每次创建新的输出纹理，ID 随资源生命周期保存。
- GPUI 的 `MetalRenderer::draw` 从当前仍存活的资源读取 ID，写入 `compose_surface.fields.preview`。辅助层和其他非模型纹理明确写为 0。
- 报告工具直接按请求 ID 关联，并验证发布时间和资源地址一致。存在歧义的旧地址关联会报告问题，不再静默给出成功结果。

这些标记只在启用 trace 时使用，正常运行不创建 label 或读取资源标签。三种对照使用同一个冻结 Release 二进制，因此都包含相同的观察开销。

## 修正后的原生 Release 对照

同一份 `mao_pro.zipzi` 副本、Angle_X、150 个可见且未锁定的 Mesh、5,159 个顶点、12,202 条边、941×1312 物理像素预览。Apple M4、16 GiB、CB27U1 4K／逻辑 1920×1080／120 Hz。用户暂停其他编译和测试；采样期间未检测到 Cargo/rustc/Clang/Xcode 编译。

三种策略各运行三轮，第二轮反转、第三轮轮换顺序。每进程 60 次预热、720 次正式输入，目标 120 Hz；不加入呈现相位锁定或等待预览的输入限速。模型位置每次完整运行都实际改变 93 个 Mesh。

“原始策略”通过同一二进制内的诊断开关恢复每次菜单查询和输入时立即通知画布；“仅菜单缓存”保持立即通知画布；“两项优化”是正常配置。它们复现两项改动的行为差异，并非重新使用旧的、缺少资源身份标记的二进制。

| 策略 | 新预览 Hz 中位数 | 全部 UI draw P95 中位数 / ms | 输入到呈现 P95 中位数 / ms |
| --- | ---: | ---: | ---: |
| 原始策略 | 112.62 | 4.993 | 48.430 |
| 仅菜单缓存 | 100.14 | 4.667 | 46.216 |
| 两项优化 | **118.67** | **4.599** | 45.770 |

| 轮 | 原始策略 Hz | 仅菜单缓存 Hz | 两项优化 Hz |
| --- | ---: | ---: | ---: |
| 1 | 118.17 | 90.63 | 118.67 |
| 2 | 104.02 | 114.16 | 117.35 |
| 3 | 112.62 | 100.14 | 118.83 |

仅降低菜单查询开销不保证帧率提高。这组中，仅菜单缓存每轮有 169／28／112 张模型帧接收后未合成；组合优化为 0／0／0，第二轮另有 2 张请求被正常拒绝。所有未合成、拒绝和无新请求终态都保留，没有只统计成功请求。

组合优化三轮输入到呈现 P95 为 **45.77／48.47／31.84 ms**，原始策略为 **40.52／48.45／48.43 ms**。中位数较低，但逐轮方向不一致，不能宣称延迟稳定改善。原始策略和仅菜单缓存的吞吐也有明显调度波动；这些数据支持本组组合优化，没有建立跨模型或任意输入相位的普遍收益。

## 仍然成立的 CPU 优化

上一轮独立详细计时未使用模型帧关联计算阶段耗时：

- `refresh_menus` P95 为 2.40 → 0.26 ms；结构创建能力按文档版本、候选编辑状态和选区复用。
- 360 次输入期间，画布构建和 paint 为 680 → 350 次；`complete_preview_edit` 成功提交预览后，等 `receive_viewport_frame` 再通知画布。
- 全部窗口绘制的开发版 UI draw P95 为 10.109 → 7.477 ms。旧的开发版模型帧率提升数字撤回，尚未用新 ID 标记重测开发版帧率。

GPU 辅助层纹理缓存原本已经避免了旧纹理的重复 GPU 提交；本轮减少的是重复 CPU 工作，并没有把 GPU 绘制次数减半。

## 验证与复现

- 报告工具 15 项测试和 benchmark 工具 9 项测试（含辅助层归因 3 项）通过，共 24 项，新增回归覆盖辅助层复用旧地址、多个有身份的模型 surface，以及无效 ID 和歧义旧 trace。
- 先前 69 项 Editor 定向测试已通过；这次新增的是诊断开关和 trace 身份，不改变普通运行时的默认刷新和菜单策略，没有重复完整 Editor/SDK 套件。
- 9 个可信进程共 6,480 次正式输入；全部有完整结束标记，丢失事件为 0，GPU 和报告 issues 为空。
- 验证每张正式测量区间的合成图像恰好有一个有效模型 ID，其余 Metal surface 为非模型 ID；同时验证纹理尺寸、真实变形、选区和顶点/边数。
- 初次暂停后的 14 个长采样和随后 12 个旧关联消融进程均保留，作为发现错误的过程记录，其模型呈现指标不参与新表格。
