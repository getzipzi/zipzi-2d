# 网格边线批量绘制

日期：2026-09-28。本页记录根据 [帧延迟排查](frame-latency-diagnosis.md) 完成的 GPUI 边线合批优化及当时的结果。正式 editor 后续已迁移到 [完整 Metal 覆盖层](mesh-overlay-rendering.md)；此处的 Path 实现保留为回退与诊断基线。

## 实现

- 同色、同线宽的网格边线合为具有独立子路径的 Path，每条边仍单独 `move_to`，不会连接原本分离的线段。顶点和选中/悬浮标记仍最后绘制。
- 每 4,096 条边分块，避开 GPUI PathBuilder 的 `u16` tessellation 索引上限；单批构建失败时退回逐边构建，避免整批有效边线丢失。
- 路径包围盒增加 1 个逻辑像素的余量，防止复制 MSAA 中间纹理时裁掉亚像素边缘；线宽仍为 1 个逻辑像素，画布 content mask 保持生效。
- 追踪时显式设置 `ZIPZI_TRACE_BATCH_MESH_EDGES=1` 使用此处的合批实现，`=0` 使用逐边实现；普通启动使用完整 Metal 覆盖层。

## 正确性检查

新增 3 项回归测试：

1. 原生 Metal 像素对照覆盖 1×/2× 像素比、0.5×/1×/2.25× 缩放、分离线段、交点、共享端点、平移原点、裁剪以及选中/悬浮标记的覆盖顺序。
2. 独立检查半透明线段和交点的 source-over 颜色，确保批量绘制保留透明度混合。
3. 对 20,001 条边检查全部 tessellation 几何，包括跨分块边界和最后一条边，确认超过单个 `u16` 缓冲容量后没有漏边。

像素比较中的逐边参考也扩大了包围盒，避免把旧路径裁掉 MSAA 边缘的行为当作标准。共享端点从分批 resolve 改为同一 pass 混合后会有局部抗锯齿差异；测试只允许该交点一个逻辑像素范围内的有限颜色变化，其余像素通道差异不超过 2/255。因此这里验证了几何、层级、裁剪与混合正确性，并不声称与旧截图逐像素相同。没有使用 computer-use；完整 UI 视觉验收仍由用户手动完成。

Workspace **72 项测试通过**（原有 CPU benchmark 仍默认忽略），报告工具 **8 项测试通过**。格式、差异空白及 vendor 补丁一致性检查通过。

## 采样输入修正

首次 Shirousagi 默认路径的两次采样都出现整段平移 `no_request`，报告工具将它们标为不完整。追踪显示模拟中键按下后、首条采样输入前出现了独立的原生鼠标移动；未按下中键的移动会取消模拟拖动。

自动 benchmark 现在只允许注入的鼠标移动驱动画布，避免 AppKit 悬浮事件或外部鼠标移动中断模拟拖动。手动追踪和普通编辑器保留原有行为。两次不完整记录保留在数据目录中，不纳入性能对比；最终对照使用相同的修正后采样器。

## 实际窗口复测

结果见 [原始数据与对照](benchmarks/2026-09-28/mesh-edge-optimization/README.md)。Release、120 Hz 目标输入、默认三缓冲和显示同步、关闭 HUD。两种模型各运行旧逐边路径和新默认路径；每组平移、缩放、透明度各预热 30 次、正式 300 次。采样期间没有并行编译或测试。

| 模型 / 操作 | GPUI GPU P50 ms | GPUI GPU P95 ms | 输入到显示 P95 ms | 显示请求数 |
| --- | ---: | ---: | ---: | ---: |
| Mao / 平移 | 7.65 → 1.14 | 8.20 → 5.21 | 56.42 → 39.89 | 300 → 297 / 300 |
| Mao / 缩放 | 7.40 → 1.15 | 8.10 → 5.30 | 55.28 → 40.69 | 300 → 288 / 300 |
| Mao / 透明度 | 7.60 → 1.16 | 8.74 → 3.01 | 56.64 → 35.69 | 278 → 300 / 300 |
| Shirousagi / 平移 | 5.99 → 1.17 | 6.60 → 5.64 | 48.79 → 40.13 | 300 → 291 / 300 |
| Shirousagi / 缩放 | 5.93 → 1.14 | 6.64 → 5.43 | 39.82 → 39.62 | 299 → 297 / 300 |
| Shirousagi / 透明度 | 5.61 → 1.15 | 6.54 → 5.52 | 40.59 → 38.78 | 297 → 288 / 300 |

Mao 的路径批次由 49–56 批降为 1 批，Shirousagi 由 17–22 批降为 1 批；两种模型的 GPUI GPU 中位耗时降低约 **80–85%**。Mao 预览交付到 UI 的中位等待由 7.43–8.03 ms 降为 0.009–0.014 ms。

默认两组共 1,800 次正式输入，其中 39 个请求被后续状态替代、未进入合成，1,761 个请求获得显示时间。Mao 旧路径实际输入约 95–106 Hz，新路径约 119–120 Hz，不能忽略这一负载频率差异来比较显示请求数量。最终轮次 GPUI GPU P95 为 3.01–5.64 ms，比早期诊断轮次更长；原始长尾全部保留。

从合成提交到系统显示的中位等待仍有约 **26–32 ms**，这次修改没有解决显示调度这一段，也不能据此宣称屏幕端稳定 120 fps。

采样从 GPUI 事件入口开始，显示时间使用 Metal drawable `presentedTime`，不包括硬件输入和屏幕像素响应。延迟分位数仅以实际显示的请求为分母；未显示请求也保留在 CSV 和摘要中，不能把输入频率当作显示帧率。

```sh
./scripts/window-benchmark.sh models/local/mao/runtime/mao_pro.model3.json target/edges-default 300 120

# 旧逐边路径作对照
ZIPZI_TRACE_BATCH_MESH_EDGES=0 ./scripts/window-benchmark.sh \
  models/local/mao/runtime/mao_pro.model3.json target/edges-baseline 300 120

cargo test --locked -p zipzi-editor --test mesh_edges
```
